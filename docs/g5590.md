## Por que não existe `/sys/class/leds/dell::kbd_backlight`

Nas variantes do G5 com backlight de cor única, o módulo `dell-laptop` cria esse
nó de LED. **Na variante RGB, não.** O RGB é um dispositivo USB HID separado,
sem driver de kernel.

Ausência desse nó neste modelo é o comportamento esperado, não um defeito. O
`alienware_wmi` também carrega, mas não cria nenhum device em
`/sys/devices/platform/` para este hardware — ele cobre perfis térmicos e G-Mode,
não iluminação.

## A tecla de backlight

A tecla dedicada emite um evento WMI que o kernel **recebe e descarta**:

```
kernel: dell_wmi: Unknown key with type 0x0012 and code 0x0000 pressed
```

O tipo `0x0012` não está no sparse keymap do `dell_wmi`, então o evento nunca
chega ao evdev. Consequência: a tecla não funciona no Linux e não há como mapeá-la
por `udev hwdb` ou `setkeycodes`, porque esses atuam sobre scancodes de evdev, e
o evento morre antes disso.

Corrigir de verdade exigiria um patch no `dell-wmi.c` adicionando o tipo `0x0012`
ao keymap. A alternativa prática é vincular um atalho do ambiente gráfico a
`awelc off` / `awelc brightness`.

Para referência, o `G15kblight-cli` assume a topologia do Dell G15, que é
`ZONES_KB = [0,1,2]` (três faixas do teclado) e `ZONES_NP = [3]` (teclado

que o mapeamento precisa verificar.

## Estado de fábrica encontrado

Na primeira sondagem (2026-09-07), o controlador tinha **2 animações gravadas**,
a primeira com id `0x61` (`DEFAULT_POST_BOOT`). Quase certamente escritas pelo
Alienware Command Center enquanto a máquina rodava Windows — elas persistem no
hardware e sobrevivem à troca de sistema operacional.

**Essas animações não puderam ser lidas de volta** (ver `protocol.md`), portanto
não existe backup delas. A primeira escrita as destrói de forma irreversível
pelo Linux; recuperá-las exigiria o Windows com o Alienware Command Center.

A resposta crua da sondagem inicial está preservada em
`probe-g5590-firmware-1.1.7.json`.

## Permissões

Sem regra udev, `/dev/bus/usb/…` é `root:root` `0664` e qualquer operação falha
com `errno 13`. Duas saídas:

1. Instalar `udev/60-awelc.rules` (recomendado) — dá acesso ao usuário da sessão
   local via `uaccess`, e a CLI passa a rodar sem privilégio
2. Rodar com `pkexec` — abre diálogo gráfico do polkit; útil para testes pontuais
   sem alterar o sistema

`sudo` puro não funciona bem a partir de sessões sem TTY: pede senha e falha com
*"a terminal is required to read the password"*. `pkexec` resolve isso quando há
um agente polkit rodando (no Plasma,
`/usr/lib/x86_64-linux-gnu/libexec/polkit-kde-authentication-agent-1`).
